在 Spring Boot + Spring Security 项目中，跨域问题处理的关键在于**CORS 配置必须在 Spring Security 的认证授权链之前生效**，否则预检请求（OPTIONS）会因未认证而被拦截。

下面会详细解释这个核心逻辑，并提供完整的代码示例。

---

### 为什么 Spring Security 让跨域变复杂了？

浏览器在发送跨域请求时，对于非简单请求（比如携带自定义头 `Authorization` 的 `POST` 请求），会先发一个 `OPTIONS` 预检请求，询问服务器是否允许跨域。

问题在于，这个预检请求**默认不携带任何身份凭证（如 Cookies 或 JWT Token）**。如果 Spring Security 的过滤器链先于 CORS 处理被执行，它看到这个请求没有认证信息，就会直接返回 401 未授权，从而无法返回正确的 CORS 响应头，导致浏览器报错。

**解决思路**：必须确保 CORS 过滤器在 Spring Security 的认证过滤器之前被调用，而 `CorsFilter` 是官方推荐的实现方式。

### 标准解决方案：在 Spring Security 中配置 CORS

最规范的做法是创建一个 `CorsConfigurationSource` 的 Bean，并将其注入到 Spring Security 的配置中。

#### 步骤一：创建 CORS 全局配置类

这个类负责定义详细的 CORS 规则。需要注意，如果允许携带凭证（如 JWT Token），`allowedOrigins` 不能使用通配符 `"*"`，而应使用 `addAllowedOriginPattern` 或指定具体域名。

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;

@Configuration
public class CorsConfig {

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        // 允许跨域的源，如果要允许所有源，且需要携带凭证，使用 OriginPattern
        config.addAllowedOriginPattern("*");
        // 允许携带凭证（如 Cookie，Authorization头）
        config.setAllowCredentials(true);
        // 允许所有请求方法
        config.addAllowedMethod("*");
        // 允许所有请求头
        config.addAllowedHeader("*");
        // 暴露前端需要获取的响应头
        config.addExposedHeader("Authorization");

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        // 对所有 API 路径生效
        source.registerCorsConfiguration("/**", config);
        return source;
    }
}
```

#### 步骤二：在 Spring Security 中启用并应用配置

在 `SecurityFilterChain` 配置中，通过 `cors()` 方法引用上面定义的 `CorsConfigurationSource`。这是最关键的一步，确保 CORS 在 Security 规则之前被处理。

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.web.cors.CorsConfigurationSource;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    private final CorsConfigurationSource corsConfigurationSource;

    public SecurityConfig(CorsConfigurationSource corsConfigurationSource) {
        this.corsConfigurationSource = corsConfigurationSource;
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // 1. 配置 CORS，引用我们的 CorsConfigurationSource
            .cors(cors -> cors.configurationSource(corsConfigurationSource))
            // 2. 按需关闭 CSRF（对于无状态API通常建议关闭）
            .csrf(csrf -> csrf.disable())
            // 3. 配置其他授权规则
            .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
            )
            // ... 其他配置（如 session 管理，添加 JWT 过滤器等）
            ;

        return http.build();
    }
}
```

### 其他可行的配置方式

除了上述标准方案，Spring Boot 还提供了以下几种处理跨域的方式，可根据场景选用：

| 配置方式                        | 特点与适用场景                                               | 与 Spring Security 的关系                                    |
| :------------------------------ | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **全局配置 `WebMvcConfigurer`** | 通过实现 `WebMvcConfigurer` 接口并重写 `addCorsMappings` 方法来配置全局CORS规则。 | 如果 Spring Security 中没有显式配置 CORS，它会尝试复用 Spring MVC 中定义的 CORS 配置，前提是 `CorsConfigurationSource` 不存在。 |
| **`@CrossOrigin` 注解**         | 在 Controller 或方法上添加注解，用于局部精细化控制，配置灵活度高。 | 可以覆盖全局配置，但大量使用会导致维护成本增加。             |
| **自定义 `CorsFilter`**         | 通过实现 `Filter` 接口，直接操作 `HttpServletResponse` 添加响应头。 | 灵活性最高，优先级也可控，但需要自己处理复杂的配置逻辑，不如使用 `CorsConfigurationSource` 方便。 |

### 总结

1.  **CORS 的处理顺序至关重要**：在 Spring Security 环境下，必须确保 CORS 逻辑在认证逻辑之前执行，这是解决跨域问题的核心。
2.  **推荐使用 `CorsConfigurationSource`**：它是 Spring 官方推荐的方式，能够在 Spring Security 的配置中无缝、安全地集成 CORS 支持。
3.  **注意“凭证”与“通配符”的冲突**：如果前端请求需要携带 Cookie 或 Authorization 头（即 `withCredentials: true` 或 `setAllowCredentials(true)`），后端不能使用 `allowedOrigins("*")`，而要指定具体域名或使用 `allowedOriginPatterns`。





**CSRF（Cross-Site Request Forgery）**，中文全称是**跨站请求伪造**，也叫 **XSRF**。

它的核心含义是：**攻击者诱导用户在不知情的情况下，利用用户已登录的身份（如 Cookie），向受信任的网站发送恶意请求，从而执行非用户本意的操作。**

下面用一个通俗的例子和代码逻辑来详细拆解。

---

### 1. 一个生动的例子（银行转账）

假设你登录了网银（`www.bank.com`），浏览器里保存了登录态的 Cookie。

- **正常情况**：你点击“转账 1000 元给朋友”，浏览器发起 `POST /transfer` 请求，携带 Cookie，银行服务器验证通过，转账成功。

- **攻击情况（CSRF）**：
  1. 攻击者给你发了一封邮件，里面包含一个隐藏的 `<img>` 标签或一个自动提交的 Form 表单，指向 `www.bank.com/transfer?to=attacker&amount=1000`。
  2. 你点击邮件时，**此时你仍然登录着网银**。
  3. 浏览器自动加载图片或提交表单时，**会带上银行网站的 Cookie**（因为 Cookie 是按域名自动携带的）。
  4. 银行服务器收到请求，验证 Cookie 通过，以为是你在操作，于是转走了 1000 元给攻击者。

**关键点**：攻击者**不需要**盗取你的 Cookie（因为浏览器自动带上了），他只需要**构造一个合法请求，并诱使你触发它**。

---

### 2. CSRF 攻击的三个必要条件

1.  **用户已登录**目标网站（A 站）。
2.  **攻击者诱导**用户访问了恶意网站（B 站）。
3.  **目标网站（A 站）仅依赖 Cookie 鉴权**，且没有额外的二次校验（如 Token、验证码、Referer 头等）。

---

### 3. Spring Security 中 CSRF 的默认行为

Spring Security **默认开启 CSRF 防护**（从 Spring Security 4.0 开始）。它的防护机制是**同步令牌模式（Synchronizer Token Pattern）**。

**工作原理**：

1.  服务器生成一个**随机且不可预测的 CSRF Token**，存储在 `HttpSession` 中。
2.  服务器将这个 Token 下发到前端（通常放在表单的隐藏域 `<input type="hidden" name="_csrf" value="xxx">` 或 Cookie 中）。
3.  前端在发起**非 GET 请求**（POST, PUT, DELETE 等）时，**必须**在请求参数或请求头（`X-CSRF-TOKEN`）中携带这个 Token。
4.  服务器收到请求后，比对请求中的 Token 和 Session 中保存的 Token，**一致则放行，否则返回 403 Forbidden**。

**为什么默认开启？** 因为对于传统的服务端渲染（如 JSP, Thymeleaf）项目，表单提交很常见，CSRF 是严重的风险。

---

### 4. 为什么在很多微服务/前后端分离项目中要关闭 CSRF？

在 **Spring Boot + 前后端分离（如 Vue/React + JWT）** 的项目中，我们通常会看到 `http.csrf().disable()`。

原因如下：

| 维度                    | 说明                                                         |
| :---------------------- | :----------------------------------------------------------- |
| **无状态（Stateless）** | JWT 项目通常不使用 `HttpSession`，Token 存储在客户端（如 LocalStorage）。Spring Security 默认的 CSRF 实现依赖 `HttpSession` 存储 Token，无 Session 时无法生效。 |
| **Token 已具备防伪性**  | JWT 本身携带签名，后端通过验签即可识别伪造请求。只要你**没有将 JWT 存储在 Cookie 中**（而是放在 Authorization 头），浏览器不会自动携带它，攻击者无法在跨站请求中自动附加 Authorization 头，天然防御了 CSRF。 |
| **移动端/非浏览器场景** | CSRF 依赖浏览器自动携带 Cookie，App 或纯后端 API 调用不涉及此问题。 |

**结论**：**如果你用 Session + Cookie 做认证（如传统 MVC 项目），请务必保留 CSRF 防护。如果你用 JWT + Authorization Header 做认证，且完全无状态，可以安全地关闭 CSRF。**

---

### 5. 针对 CSRF 的其他防护手段（除了 Spring 的 Token）

除了 Spring Security 内置的同步令牌，业界常见的 CSRF 防护方式还有：

| 防护方式                   | 原理                                                         | 适用场景                                                  |
| :------------------------- | :----------------------------------------------------------- | :-------------------------------------------------------- |
| **SameSite Cookie 属性**   | 设置 Cookie 的 `SameSite=Strict` 或 `Lax`，浏览器在跨站请求时不会发送该 Cookie。 | 现代浏览器支持，但需注意兼容性。                          |
| **检查 Referer/Origin 头** | 校验请求来源是否是本站域名。Spring Security 提供 `CsrfFilter` 支持配置 `requireCsrfProtectionMatcher` 来检查请求头。 | 大部分浏览器会携带，但可能被篡改或缺失（如 HTTPS 降级）。 |
| **双重提交 Cookie**        | 将 CSRF Token 同时放在 Cookie 和请求体中，后端比对两者是否一致。 | 不依赖 Session，适合无状态架构。                          |

---

### 6. 总结一句话

-   **CSRF 是“借刀杀人”**：攻击者利用你已登录的身份，在你不知情时替你发起恶意请求。
-   **Spring Security 默认开启防护**：要求修改状态的请求必须携带一个随机的 Token。
-   **在你的场景中**：如果使用的是 Spring Boot + JWT（Token 放在 Header 中），**建议直接 `csrf().disable()`**，因为 JWT Header 本身已经解决了同源伪造问题，保留默认的 CSRF 反而会导致非 GET 接口全部 403，且无法通过 Session 存储 Token.
